Trace as State：推理轨迹放前面，还是放后面？这个顺序差，价值 38 个百分点

Trace as State: Reasoning Traces as Conditional States for Long-Context Transformers · Xu Zou, Jie Tang (清华大学) · arXiv 2609.02702 · 2026-09-10

拿同一个模型、同一份 25 万 token 的上下文、同一条推理轨迹，做一次重读——唯一的区别，是轨迹放在上下文前面还是后面。放后面，GraphWalks Parents 任务从 29.2% 提到 43.0%；放前面，直接跳到 81.8%。这不是提示工程玄学，而是一个有指数级内存分离背书的结构性结论。

核心结论：推理轨迹里藏着"任务状态"，它必须在长上下文之前进入模型才能真正起作用。27 个模型×任务×指标组合中，前置方案赢了 26 个；GLM-5.2 在最难的任务上打满 100%。

一、顺序为什么是结构性的

自回归 Transformer 是因果处理器：读到某个位置时，后面的信息无法影响前面已经形成的表示。这带来一个顺序错配——很多长上下文任务里，关键的任务状态（当前目标、搜索边界、已排除的假设）是读到后半段才浮现的。

作者用条件状态更新任务把这个差距推到极致。设想一个处理器按顺序读一串信息，最后才告诉它"初始状态是什么"。此时它必须记住这串信息对所有可能初始状态的作用；而如果初始状态先给，它只需跟着真实的那一条状态路径走。

条件先给：⌈b⌉ 比特  vs  条件后给：⌈b·2b⌉ 比特   (b = log2|S|)

指数级差距，全部来自顺序这一个变量。这是"顺序为什么重要"的第一批最坏情况理论结果。真实任务当然不会踩满最坏情况，但它提示了一个方向：在因果结构不变的前提下，把晚发现的状态提前喂回去，可能白捡大量性能。

二、方法：两遍读，状态前置

方法出奇地简单，一个"读 → 算 → 反馈 → 重读"的循环：第一遍正常读长上下文，让模型生成推理轨迹；第二步把轨迹序列化，加上 <trace_start> 等分隔标签，得到文本 T；第三步在全新的 pass 里，把 T 放在长上下文前面重新读一遍，再回答。

对照组 Trace Append 使用完全相同的轨迹 T，只是放在上下文后面。位置是唯一变量——这个严格对照设计让"位置效应"第一次被干净地测量出来。值得注意，三个被测模型架构互不相同（DeepSeek V4 的稀疏混合注意力、Qwen 3.7 Max 的 Gated Deltanet、GLM-5.2 的 MoE+DSA），结论不绑定某家架构。

三个关键信号。其一，Random Trace 比裸奔还惨（Parents EM 掉到 14.2%）——把别的题目的轨迹放进来反而干扰模型，说明增益来自本任务的真实状态信息，不是格式。其二，Re2 重读有用但不够：简单重复原文能到 50.0%，离 81.8% 还差得远——重读的价值取决于你带什么进去重读。其三，Answer Feedback 远逊于轨迹前置：轨迹承载的过程信息（试错、排除、回退）比最终答案本身更有状态价值。

跑 5 次挑最好的答案（Oracle@5）在 Parents 上是 50%；Trace as State 一遍就到 81.8%。带状态的重读，比"多跑几次再挑"更值钱。

这是全文最值得记住的一行数。它给推理期算力分配指了一条新路：与其横向堆采样次数，不如纵向做带状态回写的迭代——把算力花在"利用已知"上，比花在"多猜几次"上性价比更高。

五、代价：token 税与 KV cache

方法不是免费的。多一遍 pass 意味着 token 和延迟接近翻倍；轨迹很长时还要截断（论文限 5 万字符）。更工程化的一点：把 T 放在上下文最前面，会破坏多轮对话里的 KV cache 前缀复用——每轮的前缀都变了。批量离线任务无所谓，实时 agent 场景要掂量这笔税。

另一个限制：它需要模型暴露原始推理轨迹。只给最终答案的 API 用不了这套，除非厂商提供别的状态接口——这也解释了为什么这是模型厂商自己最先该做的事。

六、工程意义：两个方向的白捡收益

长视频语义检索。做这个方向的人对"注意力在超长序列上全局竞争、关键信号被稀释"有切肤之痛。前置任务状态本质上是用先验压缩了搜索空间：先告诉模型"我在找什么、已经排除了什么"，再让它扫全量帧序列。这与筛选（screening）机制同构，且论文结果显示任务越难、状态前置的收益越大——正是检索场景的形状。

Agent loop。read → compute → feedback → reread，这个循环就是带状态回写的 agent harness。过去把中间结果塞回上下文开头是凭直觉，现在有了理论依据：这不是习惯，是内存意义上的最优顺序。而"路由信号 + 轨迹 + 评估反馈"共同决定下一轮训练数据的思路，也已经在同期工作（如 NeoHorse-1 的 routing harness）里出现——agent 的记忆管理和数据课程，可能正在合流成同一个问题。

七、收尾

上下文窗口越做越大，但"信息以什么顺序进入模型"这个近似免费的变量，可能比窗口本身更值得优化。条件状态更新的指数分离告诉我们：因果结构不变的前提下，让模型带着已知去重读，是结构上占便宜的做法。

留下的思考：当推理轨迹、工具调用记录、评估反馈都能变成"状态代理"，agent 的自我改进会不会收敛到同一个模式——每一轮循环，都把上一轮的状态放到最前面？
