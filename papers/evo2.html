Evo²：进化的过程，本身也该被进化

arXiv 2610.13025 · Google DeepMind × UIUC · 2026-10-09 · Chejian Xu, Shujian Zhang, Wenxuan Zhou, John Lambert, Beck Chen, Bo Li, Andrew Hard, Rajiv Mathews

自进化 agent 有两条路。一条练大脑：用自我生成的经验更新模型权重，STaR、Absolute Zero 是这条路；一条改工具箱：让模型改写自己的 harness——定义 prompt、工具、上下文、控制流的那段可执行程序，SICA、Darwin Gödel Machine 走的是这条路。两条路都跑通了，但它们从不往来。Evo² 说：这个割裂本身就是最大的浪费。

割裂的代价

权重路线和 harness 路线各有明显的边界。权重路线把经验固化进参数，但改不了 agent 的行为结构；harness 路线能重塑控制流和工具用法，但负责提出修改的那个模型始终是冻结的——它永远不会从自己提出过的修改里学到任何东西。

问题在于，权重和 harness 从来不是独立变量。模型的能力决定它提出什么修改、怎么解读执行反馈；反过来，每一次修改的成败又暴露了"哪种改动有用、为什么失败、不同改进如何互相作用"。

提出修改、诊断结果，是两种可以被训练的技能。过去没有人在训这个。

Evo² 的答案是把整个循环闭起来：更好的进化器造出更好的 harness，进化过程产生的经验又反过来训练出更好的进化器。经验同时积累在两个地方——可执行的 harness 里，和引导未来进化的策略权重里。

图 1：Evo² 框架。单一策略身兼 Proposer 和 Reflector 两职，共同进化 agent harness；harness 修改与执行结果构成训练经验，反哺策略权重；跨分支的 crossover 搜索在不同演化分支之间转移有用的策略。

双角色循环：一个人，两个岗位

harness 更新被组织成一棵树搜索。每个节点存一个 harness 及其评估记录，每条边记录相对父节点的修改。任务执行器全程冻结——这样任何性能变化都只归因于 harness 的改动，归因是干净的。

循环里有三个调用，用的是同一份参数：

Proposer Type A（自主模式）：拿到父 harness 和它的评估成绩，自己决定改什么，产出修改序列，得到初始候选。

Reflector（诊断模式）：拿到候选的源码、相对父节点的 diff、性能变化、成功与失败的执行轨迹。它先识别 Proposer 尝试的策略，再诊断遗留问题，然后三选一——revise（给一份具体修改指令，附执行证据）、crossover（从策略库挑一个 donor 策略，指令如何整合进当前 harness）、keep（定稿，不再修改）。

Proposer Type B（指令模式）：拿到 Reflector 的指令，把反馈变成能跑的代码。

这个分工是刻意设计的：Type A 练"独立发现问题"，Type B 练"把反馈翻译成实现"。Reflector 的 revision 指令质量，用它被执行后产出的 harness 性能来衡量——这也让模型自然学会"什么时候再改一刀已经不值得了"（keep 也是 learned skill）。

Crossover：好想法不许困死在自己的分支里

树搜索有个固有问题：不同分支各自发现了互补的改进，却互相看不见。Evo² 维护一个策略库，每条记录描述一个机制、它的实测效果、以及它是否已存在于当前候选中。

Reflector 拿着这个库，结合当前候选暴露出的问题，选出 donor 策略并给出整合指令；Type B Proposer 负责把外来机制适配进当前源码、与已有行为拼在一起。整合后的 harness 照常评估——成不成，数据说了算。杂交产生的子节点记的是 recipient 为树父节点、donor 策略为注记，后续还能继续被修订。

图 2：上——统一双角色循环：父 harness 从池中采样，Proposer 给出 Type A 自主修改，执行器评估后 Reflector 诊断并选择 revise / crossover / keep；下——三种数据收集机制：前缀续写（恢复有效前缀后重新生成失败后缀）、编辑抽取（从无编辑动作的 rollout 中抽取可执行修改）、crossover（donor 策略整合进 recipient）。

EvoTIDE：把进化的过程变成训练数据

这是全文最工程化的部分，也是"evolving the evolver"真正落地的地方。权重更新要轨迹，但 harness 演化的 rollout 天然残缺——EvoTIDE 用两个手段抢救：

编辑抽取：rollout 聊了半天却没输出编辑动作？去推理文本和对话记录里搜具体的文件修改，转成标准动作格式。

前缀续写：编辑序列中途某个坏了（工具调用格式错、diff 应用失败）？截断到最后一个成功应用的位置，恢复对应的中间 harness，从那个前缀重新生成。有效的前半段保住了，坏的后半段重新来。

抢救出的轨迹和正常轨迹走同一套检查：应用、启动、任务评估，一样不能少。

奖励设计同样克制：两个角色的执行奖励都是它决策造成的任务分数变化——Proposer 是 rP = V̂(h′) − V̂(h)，Reflector 是 rR = V̂(h₁) − V̂(h₀)。格式损坏、编辑无法应用、no-op 修改、无效 crossover 指令，全部负奖励。Reflector 的正收益只在轨迹里有证据表明它引入的机制真的运行过才发——防止把运气功劳记在诊断头上。

训练过程是 SFT 热启动 + 双角色交替 GRPO。SFT 混合成功的自主修改、定向修改和 Reflector 回复；在线阶段每轮冻结一份参数快照 θ̄ 作为对手——训 Reflector 时快照扮演 Proposer 供案例，训 Proposer 时快照提供 Type B 指令。两个角色轮番变强，互相抬高对方的训练数据质量。

parent pool 的设计暴露了作者的细腻：池子里同时保留最强和较弱的可执行 harness，采样权重 w(h) = εp + |V̂(h) − ½|——离中点越远（特别好或特别差）被采到越多。直觉很直白：进化器既要学会给强 harness 锦上添花，也要学会给弱 harness 雪中送炭。只会其中一样，搜索很快会偏科。

和 reHarness 对照着读

如果最近也读过 reHarness（arXiv 2610.12668），会发现这两篇在同一个母题下各占一层：reHarness 给记忆库里的经验文本加"反向修订"通道，动的是数据；Evo² 训练提出和修订 harness 修改的能力，动的是参数。但方向完全一致——经验不能只进不出，系统必须消化自己的历史。

对正在设计 agent 系统的人，一个自然的推论是：harness 进化器和记忆修订器可以共享同一套 Reflector 模式——诊断、归因、给指令、验证效果。这两个组件在架构上是同构的，工程上值得抽成同一个模式复用。

局限与保留

作者写得诚实，补几句自己的判断：

  • 任务必须有可执行的评估器。整个奖励体系建立在 V̂(h) 可以实际测量之上——生成类、评估模糊的任务喂不出干净信号。这与 reHarness 在 poker 上的失败同源：下游奖励的诊断性是所有 outcome-driven 方法的共同宿命。
  • 专有模型实验的口径：基线报各自 top-1 harness，Evo² 报两个 top harness 中较好的那个——48.3% 这个翻倍数字要打点折扣看，但趋势量级应该还在。
  • 计算成本：树搜索 + 评估 + 双角色训练，进化一轮的开销远超单次推理。这注定是离线/后台做的事，不要想在线实时进化。
  • 进化器的起点：SFT 混合数据来自底座模型自己的成功 rollout——底座太弱的话，冷启动数据的质量本身就成问题。

收尾

回到开头那两条路。Evo² 真正的贡献不是某个基准分数，而是把"进化"从一个固定流程变成了一个可学习的技能：进化器读过自己所有的成败，下次搜索时提出更好的修改、给出更准的诊断。

对你的 agent 系统，这篇给的落地启示很具体：别只攒运行日志，把每一次"改 harness 的尝试及其结果"单独建档——那是训练进化器的原始素材。今天它们只是记录，明天就是你的 Proposer 和 Reflector 的训练集。
