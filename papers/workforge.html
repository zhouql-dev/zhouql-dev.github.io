Agent 环境合成 长程工作流 可验证监督 SFT

工作区即考题：WorkForge 如何把 Agent 训练环境做得又真实又可验证

arXiv:2610.04906  ·  腾讯 LLM 部 × 复旦大学  ·  2026-10

搭一个 Agent 训练环境要几小时，造一批又只要几分钟——但几分钟造出来的东西，Agent 一眼就看穿了。当所有人都在卷模型和算法时，下一道真正的瓶颈，是"环境"本身。

专业任务和它的验证方式，从来就离不开它被完成的那片工作区——工作区决定了 Agent 能探索什么，而工作区里可观测的事实，决定了能问什么、以及能被可靠地验证什么。

一、环境的两种死法

要让大模型学会做"专业工作"，光有对话数据不够。真正的专业工作长这样：用户给一个目标，而解法藏在工作区里——Agent 必须把多个文件之间的依赖关系捋清楚，在真实的混杂文件里翻找证据，最后产出一份交付物。想让模型学会这个，就必须有承载这一切的环境。

而环境只有两条现成的路，两条都有致命缺陷。

第一条：专家手工搭建。保真度最高，但工程开销大得离谱。搭一个环境要几小时甚至几天，规模根本铺不开——这在需要几万条训练的今天，等于没有。

第二条：让模型自己合成。这条路快，造出来的却是"玩具工作区"：文件少、类型单一、关键证据就明晃晃摆在几个显眼文件里。Agent 几乎不需要探索，就能把答案凑出来。更糟的是下半场——评估标准也不建立在任何真实证据上，于是评委容易幻觉出根本不存在的要求，打分完全不可信。

WorkForge 的出发点很朴素，但顺序被彻底调了过来：先把真实工作区搭出来，再谈任务和验证。顺序一变，整件事就通了。

二、四步，把专业流程变成环境

整条管线分四个阶段，从专家脑子里的工作流，一路走到可评分的训练轨迹。下面这张图是全局。

阶段一 · 场景蓝图（Workflow Specification）

先请领域专家把工作流"蒸馏"成可复用的蓝图。一份蓝图由四样东西组成：工作流及其背景、期望交付物、所需资源及其依赖、以及领域特有的决策点。

举个例子：一位老师"出一份单元测、再针对性地讲解错题"这件事，会被结构化成"对照标准答案逐一比对、再用教材把错误归类"这样一组清晰的决策。于是这份蓝图就成了一颗种子——它能同时长出工作区、任务和验证标准。

阶段二 · 环境合成（Environment Synthesis）

一份蓝图要对应很多个"真实实现"。采集 Agent 会自己上网搜索、读参考页、下载文件、预览内容来判断相关性，把检索到的真实文件组织成一个保留原始目录结构的工作区。这就是"环境映射"。

紧接着是"环境档案"（profiling）。系统会解剖这个工作区，记录领域、各文件扮演什么角色、以及——最关键——一批可核对的、具体的事实（factual anchors）。这些事实，后面既决定了能出哪些任务，也决定了这些任务能怎么被验证。

阶段三 · 任务生成与验证设计（Task Generation）

这是全文最关键的一招。任务说明、隐藏的解法计划、以及验证用的原子 rubric，全部从阶段二抽出的"事实锚点"推导而来。

验证被拆成两路，分数分开保留：确定性要求（精确数值、可观测的工作区状态）交给程序化验证器逐条检查；开放式交付（内容质量、格式）交给LLM 语义评委，配合针对每一条 rubric 的打分指南。这样一来，验证链条永远可溯源到工作区里真实存在的东西，而不是模型凭空编出来的要求。

阶段四 · 轨迹生成（Trajectory Generation）

最后，求解 Agent 只看得到工作区和任务说明，剩下的解法计划、事实证据、验证器全部对它隐藏。它像真实使用一样交互，直到提交交付物或触到上限，最终产出一条带分数的长程轨迹，用于后训练。

更值得注意的是 27B 版本。WorkForge-27B 在 GDPval 上做到 82.4，超过了总参数接近它 15 倍的 Qwen3.5-397B-A17B（79.7），并把与前沿系统的差距压到 Claude Opus 4.8（89.1）和 GPT-5.6 Sol（90.1）身后不远处。

两个 scaling 规律

数据量越多越好。用同一套配方，分别在 1K、3.6K、8K、16K 轨迹上训练，性能单调上升。16K 组在 ALE 上拿到 28.7、WildClaw 上 29.9，分别比 1K 组高出 13.0 和 8.4 分，并在这个规模上超过了 DeepSeek V3.2、MiniMax M2.7 等更大的模型。

轨迹越长越好。把 1K 条轨迹按长度分成 0–20 轮、21–40 轮、41–60 轮三组，长轨迹组（41–60）在 ALE 上 17.5、WildClaw 上 27.8，分别比短轨迹组高出 4.2 和 5.0 分。行为上更明显：长轨迹训出来的模型平均进行 24.0 次有效工具调用，短轨迹组只有 11.7 次；触及的不同动作类型 38.3 种对 17.0 种。长轨迹让模型见识了更完整的"追依赖→找证据→造交付物"的序列。

微调后的行为变化

作者进一步解剖了 WorkForge-27B 的轨迹行为，发现它明显从"直接上手"转向了"先探索"。

微调后的模型平均访问 6.52 个外部 web 域，是基座模型的 5.3 倍；针对性的证据检索从占工具调用的 5.9% 提升到 16.2%。一次工具调用失败之后，它的推理长度从 144 字符涨到 614 字符（超过四倍）——这是在认真诊断和重新规划，而不是立刻重试。

这种转变最终体现在交付物上：五类 rubric 的得分一致上升 4.5–13 分，其中提升最大的是排版与视觉呈现（+13 分）和数值与计算准确性（+8.2 分）——恰恰是最依赖充分调查和仔细核对的两类。

五、三条消融：为什么这么设计

验证机制必须是混合的

从同一批候选任务里，用不同分数筛出三个 1K 轨迹的训练集：只用 LLM 分数、只用程序化分数、以及两者等权平均。

筛选方式ALE ScoreALE Pass@1APEX Score
只用 LLM 语义分15.624.811.18
只用程序化分14.894.810.92
混合（等权均值）22.1111.415.39

混合策略全面胜出。单一路径都会被钻空子：程序化检查抓得住数值却看不见质量，语义评委看得见质量却容易被"看起来对"糊弄。两者合力，才是有效的监督信号。

训练 harness 会带来迁移偏好

分别用 Claude Code 和 OpenClaw 生成的 8K 轨迹各训一个模型。用 Claude Code 轨迹训出来的模型，在 Claude Code 上评时 ALE 更高（24.2 对 16.1）；但在 WildClaw 上，这个顺序反了过来——OpenClaw 轨迹训出来的模型在 OpenClaw 评测下领先 6.2 分。

这说明模型学到的不只是任务知识，还有特定 harness 的工具使用习惯。训练与评测 harness 对齐时，性能往往更好。

工作区必须真实

用同一批场景蓝图，造两组工作区：一组从网上检索真实资源，一组让 LLM 合成。结构差距立刻拉开——真实资源造出的工作区文件数多 5.4 倍、文件类型多 2.4 倍，平均体积从 21.5KB 涨到 279KB。真实采集同时放大了工作区的规模和异质性，为任务构建和 Agent 探索提供了更丰富的证据空间。

六、评价与工程意义

WorkForge 最值得学的地方，是它把"顺序"当成了方法论。不是先想任务再找材料，而是先把真实工作区实例化并审计清楚，再让工作区里的事实反过来决定能问什么、能怎么验证。这一步把所有合成数据里最脆弱的环节——评估标准的正当性——重新锚回了可观测的现实。

对正在做 Agent 系统的人来说，这篇论文的信号很直接：模型的算法进步正在被"环境供给"卡住。谁能低成本地批量生产"真实 + 可验证"的工作区，谁就握住了 Agent 能力继续 scaling 的开关。

当然它也有边界。整条管线依赖领域专家提供蓝图，且真实验证需要真实资源的可得性，这两点都会限制在封闭或敏感领域（如涉密、无公开数据的行业）的复制。混合验证里 LLM 评委的质量仍是天花板，程序化验证器也只能覆盖可形式化的要求。但这些更像是"下一版本要补的洞"，而不是"方向错了"。

专业工作不是答对一道题，而是在一片真实的文件丛林里，找到那份能被验证的交付物。WorkForge 只是先承认了这件事，然后把它做成了流水线。
